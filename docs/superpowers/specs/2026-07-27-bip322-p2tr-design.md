# BIP-322 P2TR 地址验签支持

日期：2026-07-27
分支：feature/verifyaddress-eigenlayer-eoa2

## 背景与问题

`VerifyAddress` 目前对 BTC 只支持可恢复的 compact ECDSA 签名（`Bitcoin Signed Message:\n`
前缀）：从签名反推公钥，再按地址类型重建地址并比对。

P2TR（Taproot）地址用 Schnorr 签名，签名不可恢复公钥，签名载荷是 BIP-322 定义的
witness stack 序列化结果。因此现有代码路径对 P2TR 完全不适用。

现状还有一个明确缺陷：`common/utxo.go:264` 的 `^bc1[0-9a-zA-Z]{11,71}$` 正则会把
`bc1p...` 开头的 P2TR 地址误判为 `P2WSH`，随后在 `VerifyUtxoCoinSig` 走 P2WSH 多签分支，
而该分支要求非空 `script`。这是一个必须一并修掉的误判。

## 目标

- 支持 BIP-322 simple 签名的 P2TR（key-path spend）地址验签。
- 修复 `bc1p` 被误判为 P2WSH 的问题。
- 非 P2TR 地址的验签行为保持完全不变。

## 非目标

- 不支持 P2WPKH / P2SH-P2WPKH 的 BIP-322。BIP-322 的构造函数写成通用的，
  后续增加类型只需补一个验证分支。
- 不支持 BIP-322 full（proof-of-funds）形式。
- 不实现签名生成，只做验签。本工具是审计工具，不持有私钥。

## 方案

### 1. 依赖层（go.mod）

引入 `github.com/okx/go-wallet-sdk/coins/bitcoin`，并把同一 monorepo 下的其他子模块
统一到同一 revision，避免 `btcec/v2` 版本不一致：

```
+ coins/bitcoin   @v0.0.0-20260523030746-12fec6b06163
  coins/cosmos    v0.0.0-20250922... → v0.0.0-20260523030746-12fec6b06163
  coins/stacks    v0.0.0-20250922... → v0.0.0-20260523030746-12fec6b06163
  coins/starknet  v0.0.0-20241112... → v0.0.0-20260523030746-12fec6b06163
  crypto          v0.0.1            → v0.0.3 (indirect，coins/bitcoin 要求的版本)
```

`coins/bitcoin` 上游只有 v0.0.3 / v0.0.4 两个 tag，都早于 `btcec/v2` v2.3.4 的 API
变更、已无法编译；所需的修复只存在于未打 tag 的 main 分支，因此用 `@main` 引用
（Go 会把它固化成上面的 pseudo-version 写入 go.mod）。

这里**不需要** `replace`。曾误以为需要：`go mod tidy` 一度把该依赖升到 v0.0.4，但那是
因为上一次 tidy 已把当时尚未被代码 import 的 bitcoin 依赖移除，再次 tidy 时便从零解析
并选中了最高的 tag。只要主模块的 require 中有显式的 pseudo-version 且代码确实 import
了它，反复 `go mod tidy` 就不会漂移（已连续三次验证）。

连带升级（`go get` 实测结果）：`go 1.17 → 1.23.0`、`go-ethereum 1.12.2 → 1.16.1`、
`btcd 0.23.4 → 0.24.2`、`btcec/v2 2.3.2 → 2.3.4`，并新增 `blst`（CGO）、
`c-kzg-4844`、`gnark-crypto`。

必须统一 revision 的原因：`btcec/v2` v2.3.4 把 `ecdsa.SignCompact` 的返回值从 2 个改成
1 个。仓库现有的 `coins/cosmos`（8 处）和 `coins/stacks`（1 处）还在用旧签名，
只升 bitcoin 会导致 `go build ./...` 直接失败。

README 中 "requires Go (version >= 1.17)" 需同步改为 1.23。

### 2. 新增 `common/bip322.go`

SDK 已有 `VerifySimpleForBip0322`，但它的签名要求外部传入 33 字节压缩公钥，而本仓库
CSV 里 BTC 行没有公钥列（德勤格式第 6 列是 redeemScript，V6 格式该列为空；
`VerifyUtxoCoin` 第 6 个形参虽名为 `publicKey`，实际传入的是 script）。

因此复用 SDK 的构造原语，自己完成最后的 Schnorr 验证：

```go
func VerifyBip322P2TR(addr, msg, sigB64 string) error
```

步骤：

1. `bitcoin.BuildToSpend(msg, addr, mainnet)` → to_spend txid（SDK）
2. `bitcoin.NewPsbt(..., bitcoin.Bip0322Opt)` → to_sign tx（SDK）
3. `bitcoin.AddrToPkScript(addr, mainnet)` → pkScript（SDK）
4. `btcutil.DecodeAddress` → `*AddressTaproot` → 32 字节 tweaked x-only 公钥
5. `txscript.CalcTaprootSignatureHash(..., SigHashDefault, ...)`
6. `bitcoin.BtcDecodeWitnessForBip0322` 解 base64 witness stack（SDK）
7. `schnorr.ParseSignature(witness[0]).Verify(sigHash, tweakedKey)`

第 4 步是本方案的关键：P2TR 地址的 32 字节载荷本身就是 tweaked x-only 公钥，直接取用
即可绕开 publicKey 缺失。这也比 SDK 的做法更严格——签名直接绑定到地址本身，
而非绑定外部传入的公钥。

注：SDK 的 `VerifySimpleForBip0322` 中 P2PKH 分支是 `// todo` 空实现并 `return nil`
静默放行，本方案不经过该函数，不受此影响。

### 3. 修改 `common/utxo.go`

`GuessUtxoCoinAddressType` 增加 P2TR 分支，**插在 `^bc1[0-9a-zA-Z]{11,71}$` 正则之前**。
判据用 bech32m 解码结果（witness version == 1 且 program 长度 == 32），
不用字符串前缀硬匹配。

### 4. 修改 `common/verify.go`

`VerifyUtxoCoin` 中 `addrType == "P2TR"` 时跳过公钥恢复（`UtxoCoinSigToPubKey` 对
Schnorr 签名必然失败），直接调用 `VerifyBip322P2TR(addr, msg, sign1)`。

失败语义：严格报错。验不过即返回 error，计入失败行；不回退到旧的 compact ECDSA 路径。

`VerifyUtxoCoinSig` 开头 `verify.go:203` 有一处 `DecodeAddress` 失败即 `return nil` 的
静默放行。本次不改动该行为，但要确保 P2TR 不会流到那里被无声放过。

### 5. 测试 `common/bip322_test.go`

- `Bip0322Hash` 对齐官方 tagged-hash 测试向量（空串、`"Hello World"`）
- P2TR 验签正例
- P2TR 验签反例：篡改签名、换成另一个地址、空签名、非 base64 输入
- `GuessUtxoCoinAddressType` 对 `bc1p` / `bc1q` / `1...` / `3...` 的分类回归，
  锁住误判修复

测试向量取自 BIP-322 规范与 bip322-js 等通用实现中公开的向量，不自造密钥。

## 风险

1. **CGO 交叉编译（最高）**：`blst`、`c-kzg-4844` 是 CGO 依赖，而仓库需要产出
   linux-arm64 / macos 二进制且有 release pipeline。这是本方案最可能失败的环节。
   作为 fail-fast 闸门优先验证；一旦证实交叉编译不可行，停止实施并回到方案讨论，
   不擅自改动 release pipeline。
2. **geth 1.12 → 1.16**：影响所有 EVM 币种验签，靠现有测试回归。
3. **cosmos / stacks 升级**：可能存在 `SignCompact` 之外的破坏性变更，需实修。

## 依赖升级为何不可压缩

`go.mod` 的改动幅度曾被质疑，实测过能否把 `go-ethereum` 压回低版本，结论是不能：

| geth 版本 | `CGO_ENABLED=0` 结果 |
| --- | --- |
| 1.12.2（原版） | 失败：`crypto/signature_nocgo.go` 使用旧的 `btc_ecdsa.SignCompact` 两返回值 API |
| 1.13.0 / 1.13.15 / 1.14.0 / 1.14.13 | 失败：`go-kzg-4844` 与被抬高的 `gnark-crypto v0.18.0` 交叉不兼容 |
| 1.16.1 | 通过（当前采用） |

注意 1.12.2 在 `CGO_ENABLED=1` 下可以编译，因为走的是 `signature_cgo.go`；而 release
用 `CGO_ENABLED=0`，恰好命中 `signature_nocgo.go`。仅在本机构建验证会漏掉这一点。

根因是 `coins/bitcoin` 强制 `btcec/v2` v2.3.4，其 `SignCompact` 签名变更会连锁传播：
先打断旧版 cosmos / stacks，再打断旧版 geth 的 no-CGO 分支。压回低版本需要手工钉住
gnark-crypto / kzg 一串传递依赖，脆弱且不利于审计。

因此在采用 SDK 的前提下，本 spec 记录的升级集是最小可行集。若要让 `go.mod` 零改动，
唯一途径是改为在 `common/` 内自建（现有 btcd v0.23.4 已具备全部所需 Taproot 符号），
代价是多约 55 行仓库内代码。

## 决策记录

- 选择引入 SDK 而非在 `common/` 内自建（约 100 行、零新依赖）：已向用户呈现两条路线的
  实测代价，用户在知悉编译破坏、go 1.23、CGO 依赖的前提下选择 SDK 路线并接受
  连带依赖升级的工作量。
- 失败语义选择严格报错而非宽容回退：本工具是审计工具，回退会掩盖真实的签名问题。
- 在得知依赖升级不可压缩后，仍确认保留 SDK 路线，接受 `go.mod` 的改动幅度。
